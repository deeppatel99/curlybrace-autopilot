## Issues
- [severity: high] [location: section "Decision 2", asset "GitHub OIDC subject claims…", Bicep `subject`, asset "60-Second Revision"] Since July 15, 2026, GitHub gives every new, renamed or transferred repository on github.com an immutable default `sub` that includes the owner ID and repo ID: `repo:OWNER@OWNER_ID/REPO@REPO_ID:environment:production`. A reader who creates a repository today and copies `repo:${githubRepo}:environment:production` gets `AADSTS70021`. The subtitle promises "exact subject claims", and these subjects are now wrong for any new repository. -> Add a paragraph to Decision 2 about the two formats: legacy name-based subjects for older repos, and immutable ones for repos created, renamed or transferred after July 15, 2026, or opted in. Update the table rows. Change the Bicep to take `githubOwnerId` and `githubRepoId` parameters and build `repo:${owner}@${ownerId}/${repo}@${repoId}:environment:production`. Explain that immutable subjects also stop "subject recycling" (a different repository later producing a token that matches your credential), which supports your security argument. Link Microsoft's migration guide. Add "new repos use the immutable sub" to the revision card.
- [severity: medium] [location: cover asset, section "The critical code" workflow, asset "60-Second Revision"] `azure/login@v2` is out of date. The action's README says "Customers are strongly encouraged to use the latest v3 release." v2 now gets security fixes only. -> Change all three places to `azure/login@v3`. Also check whether `actions/checkout@v4` and `azure/webapps-deploy@v3` are still the current major versions.
- [severity: medium] [location: section "Azure DevOps: convert first, then fix the scripts"] This contradicts Decision 1. The conversion tool keeps the app registration that Azure DevOps created automatically. That is the kind of identity where "someone can add a client secret back", and the article never says to delete the original secret. The title says federation "deletes it", and in this path nothing is deleted. -> Say plainly that conversion is a quick win that leaves an app registration in place. Add a step: after the 7-day revert window, delete the old client secret from the app registration (**Certificates & secrets**). Later, move the connection to the managed-identity option so it matches Decision 1. Or present the managed-identity connection as the recommended path and conversion as the stopgap.
- [severity: medium] [location: section "Results, and what I'd do differently"; "My position" paragraph] "If I were starting over… instead of clicking through the portal and importing them later" reads as the author's own migration. "the migration takes an afternoon" is a claim nothing supports. The author's notes back neither, and the format says not to claim unsupported results. -> Reframe as design advice ("Declare the identities in Bicep from day one; portal-created credentials are hard to bring under review later"). Change "takes an afternoon" to something you can defend, such as "is a small, mostly mechanical change per pipeline". Drop both unless the notes confirm a real migration.
- [severity: medium] [location: asset "Who can deploy to production" (Resources layer), section "Decision 3"] "The App Service and nothing else the identity can touch" is false for a resource-group scope. Website Contributor on the RG covers every site in the RG and includes `Microsoft.Web/sites/*`, which allows reading app settings and connection strings, plus `Microsoft.Insights/components/*` and `Microsoft.Resources/deployments/*`. -> Reword to "Only the resources in rg-orders-prod". Alternatively, scope the role assignment to the site (`scope: site` in Bicep) and say that's the tighter option. Mention that `sites/*` can read app settings, which ties into your third "do differently" point.
- [severity: medium] [location: section "Decision 1" and table row "Tag push", revision card "no wildcards"] "Wildcards aren't supported in any field" holds for standard federated credentials only. Entra now has *flexible* federated identity credentials (`claimsMatchingExpression` with `matches`) on app registrations, which allow patterns such as `repo:org@id/repo@id:*`. -> Add one sentence: "Flexible federated credentials on app registrations can pattern-match; managed identities can't. That's a real trade-off of Decision 1: you give up wildcards to make sure no one can add a secret back." This makes the decision section stronger.
- [severity: medium] [location: section "Azure DevOps…" Terraform snippet] The snippet doesn't set `ARM_SUBSCRIPTION_ID`. azurerm provider 4.x requires a subscription ID, so the snippet fails as written on current providers. `ARM_OIDC_TOKEN` passes a raw `idToken` that can't be refreshed, so a long `terraform apply` hits the same `AADSTS700024` you describe later. -> Add `export ARM_SUBSCRIPTION_ID=$(az account show --query id -o tsv)`. Add one line: for long applies, use the azurerm provider's Azure DevOps service-connection OIDC support (`ARM_ADO_PIPELINE_SERVICE_CONNECTION_ID` plus `SYSTEM_ACCESSTOKEN`), which can request fresh tokens.
